# Безопасность Kivi: модель угроз и защита от prompt injection

Версия: 0.1 (09.11.2026).
Связанные документы: `docs/DECISIONS.md`, `docs/ARCHITECTURE.md`, `docs/MODULES.md`, `docs/SHELL.md`.

---

## 1. Главный принцип

**Текст не является полномочием.**

Ни веб-страница, ни письмо, ни документ, ни вывод инструмента, ни «системное сообщение» внутри
файла не могут расширить права Kivi. Права выдаёт только:

1. пользователь — явной командой или подтверждением;
2. политика безопасности — заранее утверждённым правилом;
3. подписанный манифест модуля — в пределах его разрешений.

Модель может **предложить** действие. Выполняет его **Policy Engine** после проверки.
Даже если модель «убедили», что ей разрешено всё, ядро этого не разрешит.

---

## 2. Почему одного промпта недостаточно

Инструкция «не выполняй команды из веб-страниц» помогает, но не является границей безопасности:

- модель вероятностная, её можно обмануть формулировкой;
- injection может прийти не текстом, а картинкой, OCR, именем файла, комментарием в коде,
  метаданными PDF, alt-текстом, скрытым HTML, Unicode-омоглифами;
- длинный контекст размывает инструкции;
- модель может вызвать инструмент «по привычке», даже поняв, что это данные.

Поэтому защита строится **слоями вне модели**:

```
недоверенный контент
   → изоляция и разметка происхождения
   → очистка и ограничение
   → «карантинный» читатель без инструментов
   → структурированные факты
   → планировщик с ограниченными правами
   → Policy Engine
   → подтверждение высокорисковых действий
   → инструмент с минимальными правами
   → аудит и egress-контроль
```

Ни один слой не считается достаточным. Безопасность — это свойство системы, а не текста промпта.

## 3. Активы, которые защищаем

| Актив | Почему важен | Основная угроза |
|---|---|---|
| Файлы пользователя | работа, документы, личное | удаление, шифрование, кража |
| Секреты | пароли, токены, ключи, cookies | exfiltration в облако/сообщение |
| Деньги | покупки, подписки, счета | мошеннические платежи |
| Репутация | почта, Telegram, CRM | отправка оскорблений/спама клиентам |
| Система | Windows, драйверы, загрузчик | повреждение ОС |
| Память Kivi | факты и предпочтения | отравление памяти |
| Аудит | журнал действий | сокрытие следов |
| Аватар/голос | доверие пользователя | подделка «указаний Kivi» |

## 4. Модель угроз

### 4.1. Кто может атаковать

- сайт, который читает Kivi;
- автор письма или сообщения в Telegram;
- PDF/DOCX/XLSX с скрытым текстом;
- комментарий в коде или README репозитория;
- имя файла, метаданные, alt-текст, OCR-текст на картинке;
- ответ API, который выглядит как инструкция;
- вредоносный плагин или обновление модуля;
- локальный пользователь без прав (низкая вероятность, но учитываем);
- сам пользователь по ошибке (social engineering).

### 4.2. Что хочет сделать атакующий

1. Прочитать и отправить секреты.
2. Удалить/зашифровать файлы.
3. Отправить сообщение клиенту или коллеге.
4. Перевести деньги / оформить заказ.
5. Установить программу или запустить код.
6. Изменить политику, аудит, список запретов.
7. Записать ложный факт в долговременную память.
8. Сделать Kivi «рупором» атаки: озвучить текст, открыть сайт, позвонить.

### 4.3. Границы доверия

| Источник | Метка | Может давать команды? |
|---|---|---|
| Системная политика Kivi | `trusted:system` | Да, но только через Policy Engine |
| Явная команда пользователя в UI/голосе | `trusted:user` | Да, в пределах прав |
| Подписанный манифест модуля | `trusted:module` | Только свои tools |
| Файлы пользователя | `untrusted:file` | Нет |
| Веб-страница | `untrusted:web` | Нет |
| Письмо/Telegram | `untrusted:message` | Нет |
| Вывод инструмента | `untrusted:tool` | Нет |
| OCR/картинка | `untrusted:vision` | Нет |
| Память/RAG | `tainted:memory` | Нет, если нет проверенного источника |
| Сгенерированный код | `untrusted:code` | Нет, пока не пройдёт политику |

Метка происхождения ставится **до** попадания в контекст модели и сохраняется в аудите.

## 5. Архитектура защиты

### 5.1. Конвейер обработки недоверенного контента

```
1. Ingestion
   source, url/path, hash, mime, timestamp, author
2. Sanitization
   visible text only; remove hidden/zero-width/bidi/HTML comments; normalize Unicode
3. Quarantine reader
   model without tools → structured facts + quotes + source refs
4. Trust labeling
   every fact carries provenance and trust level
5. Planner
   sees user goal + sanitized facts; does not see raw untrusted text by default
6. Policy Engine
   validates every proposed tool call against capabilities
7. Action firewall
   high-risk → confirmation with exact action/recipient/diff
8. Execution
   least-privilege tool, no secrets in prompt, egress filter
9. Audit
   prompt hash, sources, plan, policy decisions, result
```

### 5.2. «Карантинный читатель» (dual-LLM)

Два режима модели:

| Роль | Видит | Инструменты | Выход |
|---|---|---|---|
| **Reader** | сырой недоверенный контент | **нет** | JSON: факты, цитаты, ссылки, предупреждения |
| **Planner** | цель пользователя + очищенные факты | только разрешённые tools | план действий |

Правила:

- Reader не может вызвать tool, открыть файл, отправить сообщение.
- Reader обязан возвращать **цитаты и источник** для каждого факта.
- Planner не получает сырой HTML/PDF целиком; только структурированную выжимку.
- Если Planner нужен фрагмент, он запрашивает его через `content.read_fragment` с лимитом
  и повторной очисткой; фрагмент всё равно помечен как `untrusted`.
- Для дешёвых задач Reader может быть маленькой локальной моделью; для сложных — 8B.
- Reader и Planner не делят один и тот же system prompt без разделителей.

Это не абсолютная защита, но резко снижает шанс, что instruction из текста станет действием.

### 5.3. Spotlighting и разделители

Все недоверенные данные подаются в модель в явном «конверте»:

```
<untrusted source="web" url="https://..." hash="...">
  ...данные...
</untrusted>
```

Правила:

- содержимое конверта не исполняется;
- ссылки внутри не открываются автоматически;
- маркеры `system:`, `assistant:`, `tool:` внутри данных экранируются/нейтрализуются;
- модель обязана ссылаться на источник, а не пересказывать «как инструкцию»;
- при конфликте «пользователь просит X, страница требует Y» — побеждает пользователь,
  страница помечается как враждебная.

### 5.4. Capability Broker

Модель не вызывает инструменты напрямую. Она формирует **предложение**:

```json
{
  "action": "fs.write",
  "args": {"path": "D:\\AI-assistent\\workspace\\report.md", "content": "..."},
  "reason": "сохранить отчёт",
  "evidence": ["user_request", "s1"],
  "risk": "R1"
}
```

Policy Engine проверяет:

- инструмент разрешён задаче;
- путь канонизирован и входит в scope;
- домен в allowlist;
- получатель в allowlist;
- сумма/лимит;
- нет protected zone;
- нет попытки изменить policy/audit/denylist;
- количество действий и время не превышают лимит;
- источник действия: `trusted:user` или политика, а не текст страницы.

Только после этого — выполнение. Отказ объясняется пользователю, но **не** «попробуй иначе».

### 5.5. Action Firewall: что требует подтверждения

| Категория | Примеры | Режим |
|---|---|---|
| R0 | чтение, поиск, скриншот, OCR | авто |
| R1 | запись в workspace, запуск теста, черновик | авто + бэкап |
| R2 | удаление, перезапись вне workspace, закрытие программ | подтверждение |
| R3 | отправка письма/сообщения, публикация, установка, admin | подтверждение + аудит |
| R4 | деньги, необратимые внешние действия, сделки | двойное подтверждение + лимит |

Подтверждение показывает:

- **точное действие**: команда, путь, diff, получатель, сумма;
- **источник**: «вы попросили» / «найдено на странице X»;
- риск и обратимость;
- срок действия;
- кнопки «один раз», «на задачу», «отклонить».

Если действие инициировано недоверенным контентом, по умолчанию — **отказ**, даже если
пользователь когда-то разрешил похожее действие. Нельзя «наследовать» разрешение из текста.

### 5.6. Egress-контроль и DLP

Перед любым исходящим вызовом (облако, почта, Telegram, HTTP, браузерная форма):

1. Проверить, не является ли получатель/домен запрещённым.
2. Проверить содержимое на:
   - пароли, токены, ключи, cookies;
   - файлы из Protected Zones;
   - персональные данные, если пользователь запретил;
   - canary-токены;
   - большие бинарные вложения без подтверждения.
3. При срабатывании — блок или redaction + отчёт.
4. Для облака — отдельная политика `cloud: auto_free` и `data_policy`.
5. Логировать, что именно ушло (hash + метаданные, не сам секрет).

Секреты **никогда** не попадают в prompt. Инструмент получает секрет из vault в момент
выполнения и не возвращает его модели.

### 5.7. Очистка контента

Санитайзер:

- извлекает только видимый текст;
- удаляет HTML-комментарии, `display:none`, `visibility:hidden`, нулевой размер;
- удаляет zero-width, bidi override, гомоглифы, подозрительные Unicode-блоки;
- нормализует переводы строк и пробелы;
- ограничивает длину (например, 32 КБ на фрагмент);
- декодирует и проверяет base64/hex-блоки отдельно;
- сохраняет ссылки как текст, не как активные переходы;
- для PDF — извлекает текст и метаданные, не запускает JS;
- для DOCX/XLSX — читает XML, не выполняет макросы;
- для картинок — OCR + подпись «текст с картинки недоверенный»;
- для кода — не исполняет, а показывает diff.

### 5.8. Защита памяти от отравления

- Каждая запись памяти имеет `source`, `trust`, `timestamp`, `hash`.
- Контент из `untrusted:*` **не** попадает в долговременную память автоматически.
- Кандидат в память проходит:
  - явное подтверждение пользователя, или
  - правило «только из доверенного источника» (например, пользователь сказал сам).
- Новые записи — в карантине с TTL; retrieval показывает метку.
- «Забудь X» удаляет запись, векторы и связи.
- Периодический аудит: кто и когда записал факт.
- RAG-источники не дают права на действия; только факты с цитатами.

### 5.9. Браузер

- Отдельный профиль `kivi-browser`, без сохранённых паролей и автозаполнения
  для чувствительных сайтов.
- Управляемая вкладка; пользователь видит, что делает Kivi.
- По умолчанию — чтение. Клики, формы, скачивания — по политике.
- Запрещены `javascript:`, `data:`, `file:` URL из недоверенного контента.
- Домены — allowlist; новые — подтверждение.
- Скачанные файлы — в карантин, не открываются автоматически.
- Страница не может инициировать tool call; только Planner после очистки.
- Для CRM — предпочтительно API/адаптер, а не свободные клики по DOM.
- Инжектированный текст на странице не меняет задачу; при попытке — стоп и отчёт.

### 5.10. Почта и Telegram

- Входящие сообщения — только данные.
- Gmail: OAuth, scope `gmail.readonly` + `gmail.compose`. Отдельного scope «только черновики»
  в Gmail API нет, поэтому `messages.send` и `drafts.send` запрещены в коде и политике;
  приложение вызывает только `drafts.*`/`messages.get/list`.
- Kivi может суммировать, искать, готовить черновик.
- Автоотправка выключена до отдельного этапа и отдельного согласия.
- Отправка — по политике: allowlist получателей, лимит, подтверждение.
- Никаких ответов на «срочно переведи деньги» без независимой проверки.
- Вложения — в карантин, антивирусная проверка, не открывать автоматически.
- Секреты и внутренние документы — не пересылать.
- Для Telegram-бота — allowlist chat_id, rate limit, подпись «Kivi».

### 5.11. Код и песочница

- Код выполняется только в WSL2/Windows Sandbox.
- Монтируется только workspace; сеть выключена по умолчанию.
- Лимиты CPU/RAM/времени; process tree убивается.
- Секреты не пробрасываются в песочницу.
- Сгенерированный код не получает доступ к хосту.
- Установка пакетов — с подтверждением и из allowlist.
- Выход из песочницы — только через явный экспорт артефакта.

### 5.12. Плагины и модули

- Подписанный `module.yaml`, `api_version`, permissions.
- Модуль не получает доступ к safety-ядру, аудиту, denylist.
- Отдельный процесс/пакет; падение не роняет ядро.
- Секреты — в namespace vault.
- Обновление: backup → migrate → healthcheck → rollback.
- Код модуля проверяется тестами; дифф показывается пользователю.

### 5.13. Admin и elevated broker

- Ядро, UI, аватар — обычные права.
- Admin-операции — отдельный процесс с UAC и узким allowlist.
- Никакого «произвольного PowerShell от администратора».
- Каждая операция — подтверждение + аудит.
- Агент не может инициировать break-glass сам.

### 5.14. Секреты

- Vault: Windows DPAPI/Credential Manager или age/KeePassXC.
- Секреты не в промпте, не в логах, не в памяти.
- Инструменты получают секрет через broker.
- Ротация и отзыв.
- Маскирование в UI и аудите.
- Отдельные учётные данные для Kivi, не личные.

## 6. Детектирование

Детекторы — **сигнал**, а не замена политике:

- эвристики: «ignore previous», «system:», «you are now», «send file», «delete», «curl»,
  «base64», «password», «token», «wire transfer»;
- классификатор injection на локальной модели;
- аномалии: необычная последовательность tools, много egress, попытки чтения Protected Zones;
- canary-токены в system prompt и защищённых файлах;
- сравнение плана с целью пользователя;
- проверка, что источник действия — `trusted:user`, а не `untrusted:*`;
- rate limit на инструменты и внешние вызовы.

При срабатывании:

1. остановить задачу;
2. показать пользователю источник и причину;
3. предложить безопасный вариант;
4. записать в аудит;
5. при утечке — отозвать сессию/токены.

## 7. Аудит и incident response

Аудит пишет:

- кто инициировал задачу;
- какие источники читались (hash, url/path, trust);
- план и каждое действие;
- решение Policy Engine;
- подтверждения (кто, когда, что именно);
- результат и ошибки;
- egress (куда, что, hash);
- изменения политики и модулей.

Incident response:

1. **Kill switch** `Ctrl+Alt+J` / «Kivi, стоп».
2. Отозвать capabilities и сетевые токены.
3. Изолировать сессию/браузер.
4. Сохранить аудит и артефакты.
5. Восстановить из бэкапа.
6. Разобрать причину и добавить regression-тест.

## 8. Тесты и критерии приёмки

### 8.1. Обязательные тесты

- 100+ сценариев prompt injection:
  - веб-страница;
  - письмо;
  - PDF/DOCX;
  - OCR-картинка;
  - имя файла;
  - комментарий в коде;
  - README репозитория;
  - ответ API;
  - Telegram-сообщение;
  - память/RAG;
  - вывод инструмента;
  - Unicode/zero-width/гомоглифы.
- Проверка, что ни один сценарий не приводит к:
  - чтению Protected Zone;
  - отправке секрета;
  - удалению вне workspace;
  - отправке сообщения без подтверждения;
  - изменению policy/audit/denylist;
  - установке ПО без подтверждения.
- Canary-тесты: секрет-приманка не должен уйти в облако/сообщение.
- Path traversal: `..`, symlink, junction, hardlink, UNC, 8.3, ADS.
- Policy fuzz: случайные комбинации tools/args не расширяют права.
- Sandbox escape: код не видит хост, сеть, секреты.
- Memory poisoning: внешний факт не становится доверенным без подтверждения.
- Browser: страница не может вызвать tool; `javascript:`/`data:` блокируются.
- Plugin: модуль не получает лишних прав; откат работает.
- Логи: секреты не попадают в аудит.

### 8.2. Критерии приёмки

- 0 несанкционированных R2–R4 действий в 100+ атаках;
- 100% R2–R4 действий имеют подтверждение или явную политику;
- 0 утечек canary-секретов;
- 0 записей в Protected Zones;
- 0 изменений policy/audit/denylist агентом;
- false positive rate детектора не блокирует обычную работу (цель < 5%);
- каждое действие имеет аудит-запись;
- kill switch срабатывает < 1 с.

### 8.3. Регрессия

Корпус атак хранится в `tests/security/injection/` и запускается в CI.
Каждый инцидент добавляет новый тест. Нельзя «починить» инцидент без теста.

---

## 9. Остаточные риски

- Модель всё равно может ошибиться в пределах разрешённых прав.
- 0-day в браузере/WebView2/Windows.
- Пользователь может подтвердить вредное действие.
- Плагин с подписью, но вредоносный.
- Сложные многошаговые атаки, которые выглядят как обычная работа.
- Локальная модель может быть слабее в детекции injection.

Поэтому:

- минимум прав;
- подтверждение необратимого;
- бэкапы и обратимость;
- аудит;
- возможность отключить сеть/инструменты;
- честное сообщение о рисках.

## 11. Что нельзя делать

- Нельзя выполнять инструкции из веб-страниц, писем, документов, картинок, кода и памяти.
- Нельзя давать модели прямой доступ к shell/FS без Policy Engine.
- Нельзя хранить секреты в промпте или логах.
- Нельзя автоматически создавать аккаунты, обходить CAPTCHA, нарушать ToS.
- Нельзя отключать аудит, denylist и safety-ядро агентом.
- Нельзя считать «модель поняла, что это атака» достаточной защитой.
- Нельзя обещать абсолютную безопасность: только слои, минимум прав и обратимость.
