# Benchmark: переключение моделей Gateway

Дата: 2026-11-10. Машина: Windows 11, NVIDIA GPU с 8192 МБ VRAM (NVML),
Ollama на `127.0.0.1:11434`. Модели измерены на этой машине:
`qwen3.5:4b` (router, ~3800 МБ) и `qwen2.5-coder:7b` (code, ~4700 МБ при 8K).
Рабочий стол занимает ~3.1 ГБ VRAM.

## Команда

```powershell
.venv\Scripts\python.exe scripts\bench_gateway.py `
  --switches 20 --models qwen3.5:4b,qwen2.5-coder:7b --timeout 600 --margin-mb 256
```

Каждое переключение: `acquire` → замер свободной VRAM → `release` → ожидание
фактического возврата памяти. Обе модели не помещаются вместе, поэтому каждое
переключение — это eviction предыдущей.

Перед запуском контекст модели фиксируется по registry (`num_ctx=4096/8192`)
через `options` при загрузке. Без этого Ollama брала дефолт модели (до 262144),
раздувала модель до 14 ГБ и уходила в CPU/swap.

## Что показал первый прогон

Первый прогон без `num_ctx` прошёл 20/20, но свободная VRAM падала до 26 МБ:
Ollama грузила модель с контекстом 262144 и частично вытесняла её в CPU.
Второй прогон с контекстом 4096/8192 и margin 512 дал 10 отказов из 20:
`qwen2.5-coder:7b` требовал 4800 + 512 МБ, а фактически помещается в ~4.7 ГБ.
После измерения реального footprint'а и снижения margin до 256 МБ все
20 переключений проходят с запасом 448 МБ.

## Выводы

1. **Приёмка «20 переключений без OOM» пройдена** для пары chat/code.
2. После `release` VRAM возвращается: минимум 5141 МБ свободно, то есть модель
   действительно выгружается. Сразу после ответа `/api/generate` память
   освобождается не мгновенно — benchmark ждёт до 10 с.
3. Контекст нужно фиксировать при загрузке: `ModelSpec.context` → `num_ctx`.
   Иначе локальная модель может занять в 3–4 раза больше VRAM, чем ожидается.
4. Safety margin 512 МБ слишком консервативен для 8 ГБ карты с рабочим столом
   на 3.1 ГБ; 256 МБ даёт фактический запас ~450 МБ и пропускает 7B-модель.
5. Время загрузки нестабильно (3–6 с на тёплом кэше, до 27 с на холодном).
   Стриминг уже даёт отзывчивость; нужен индикатор «загружаю модель».
